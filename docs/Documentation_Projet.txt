1. OBJECTIF ET HYPOTHÈSES
==============================================================================

Objectif : construire une application de bureau Windows qui reproduit l'essentiel de
PowerPoint : créer des diapositives, y placer du texte, des formes et des images, les
mettre en forme, les présenter en plein écran, et surtout OUVRIR et ENREGISTRER de vrais
fichiers PowerPoint (.pptx).

Équipe :
  - Membre 1 (chef technique)      : niveau avancé  -> parties les plus difficiles
  - Membre 2                       : niveau avancé  -> parties les plus difficiles
  - Membre 3                       : niveau intermédiaire -> parties de difficulté moyenne
  - Membre 4                       : parties moins complexes (mais pas triviales)

Hypothèses (à corriger si elles sont fausses) :
  H1. Le membre 3 est de niveau intermédiaire (entre M2 et M4).
  H2. Tout le monde développe sous Windows (WPF ne fonctionne que sous Windows).
  H3. Les NOMS dans le code (classes, méthodes, variables) sont en anglais, comme le veut
      la convention de l'industrie ; les COMMENTAIRES, la documentation, les messages de
      commit et l'interface utilisateur sont en français.
  H4. Il n'y a pas de date limite : le projet est mené le plus vite possible. On livre d'abord
      ce qui rend l'application utilisable comme un PowerPoint de base (priorité P1), puis on
      ajoute les autres fonctions (P2, puis P3). Le plan (section 8) suit cet ordre de priorité,
      sans dates ni semaines.
  H5. Le Membre 3 est le responsable GUI (interface graphique) : il possède tous les fichiers
      XAML de vues et de styles, pour garantir un aspect cohérent (section 5). Proposition à
      confirmer ; si l'équipe préfère un autre membre (ex. M1), il faut réattribuer ces
      fichiers dans les sections 5 et 6.

2. RECHERCHE : QUE DOIT FAIRE UNE RÉPLIQUE « EFFICACE » DE POWERPOINT ?
==============================================================================

2.1 Méthode
Synthèse de : (a) l'organisation de PowerPoint (onglets Accueil, Insertion, Création,
Transitions, Diaporama), (b) la norme Open XML (ECMA-376 / ISO 29500) qui décrit le format
.pptx, (c) la documentation du SDK Open XML de Microsoft et des versions actuelles de .NET.

2.2 Les 6 fonctions qui définissent un logiciel de présentation
  1. Gérer un document de plusieurs diapositives (ajouter, supprimer, réordonner).
  2. Éditer visuellement (placer, déplacer, redimensionner des objets à la souris).
  3. Mettre en forme (police, couleurs, remplissage, contours, fond).
  4. Présenter (mode diaporama plein écran).
  5. Lire / écrire le format standard .pptx (sinon ce n'est pas « PowerPoint »).
  6. Offrir le confort attendu : annuler / rétablir, copier / coller, raccourcis clavier.
Si l'une de ces six fonctions manque, l'application ne sera pas jugée « effective ».

2.3 Fonctionnalités par priorité
  P1 = indispensable (sans cela ce n'est pas un PowerPoint)   <- À LIVRER ABSOLUMENT
  P2 = important (qualité)                                    <- À FAIRE si P1 terminé
  P3 = bonus                                                  <- seulement s'il reste du temps

 --- P1 : INDISPENSABLE ---
  Fichiers
   F01  Nouvelle présentation (format 16:9 ou 4:3)
   F02  Ouvrir un .pptx (texte, formes, images, fond)
   F03  Enregistrer / Enregistrer sous en .pptx, rouvrable dans PowerPoint SANS message de
        réparation
   F04  Alerte si modifications non enregistrées ; liste des fichiers récents
  Diapositives
   F05  Panneau de vignettes à gauche ; cliquer pour changer de diapositive
   F06  Ajouter, supprimer, dupliquer, réordonner (glisser-déposer) des diapositives
   F07  Choisir une disposition (Titre, Titre + Contenu, Deux contenus, Vide)
  Édition sur la diapositive (canvas)
   F08  Insérer une zone de texte ; modifier le texte directement dans la zone
   F09  Insérer des formes (rectangle, ellipse, triangle, ligne, flèche)
   F10  Insérer une image (PNG / JPG) depuis le disque
   F11  Sélectionner, déplacer, redimensionner (8 poignées), pivoter, supprimer
   F12  Copier, couper, coller, dupliquer des éléments
   F13  Ordre d'empilement (premier plan / arrière-plan)
   F14  Annuler / Rétablir (Ctrl+Z / Ctrl+Y), sur toutes les actions d'édition
  Mise en forme
   F15  Texte : police, taille, gras, italique, souligné, couleur, alignement, puces
   F16  Forme : couleur de remplissage, couleur et épaisseur du contour
   F17  Fond de diapositive (couleur)
  Présentation
   F18  Diaporama plein écran (F5) : suivant / précédent (flèches, clic), Échap pour quitter
  Interface
   F19  Interface type PowerPoint : ruban ou barre d'outils à onglets, vignettes, zone
        centrale, volet de notes, barre d'état
   F20  Raccourcis standards (Ctrl+N / O / S / C / V / X / Z / Y, Suppr, F5)

 --- P2 : IMPORTANT ---
   F21  Notes du présentateur (affichage, édition, lecture / écriture dans le .pptx)
   F22  Aligner / distribuer ; guides d'alignement magnétiques
   F23  Grouper / dissocier des éléments
   F24  Transitions simples (fondu, balayage) : lecture, écriture, rendu en diaporama
   F25  Export des diapositives en images PNG
   F26  Tableaux simples
   F27  Palettes de couleurs / thèmes prédéfinis
   F28  Conserver (sans les afficher) les objets non gérés (graphiques, SmartArt...) pour
        ne pas les perdre quand on enregistre : indispensable pour ne pas « casser » un
        fichier existant
   F29  Zoom de la zone d'édition, « ajuster à la fenêtre »

 --- P3 : BONUS ---
   F30  Export PDF            F31  Rechercher / remplacer
   F32  Masque de diapositives simplifié     F33  Animations basiques
   F34  Vue « trieuse de diapositives »      F35  Impression
   F36  Mode présentateur (2 écrans)         F37  Sauvegarde automatique

2.4 Hors périmètre (on ne le fait PAS, et on le dit dans le rapport)
  SmartArt, graphiques, audio / vidéo, macros VBA, collaboration en temps réel,
  commentaires, animation « Morph », correction orthographique, effets 3D / ombres
  complexes, fidélité visuelle à 100 % avec PowerPoint (polices et effets approchés).

2.5 Ce qu'il faut savoir sur le format .pptx AVANT de coder
  - Un .pptx est une archive ZIP contenant des fichiers XML (norme Open XML). Astuce :
    renommer un .pptx en .zip et l'ouvrir pour voir son contenu.
  - Parties importantes de l'archive :
      /ppt/presentation.xml        liste des diapositives + taille de page
      /ppt/slides/slideN.xml       contenu de chaque diapositive
      /ppt/slideLayouts/           dispositions (Titre, Titre + Contenu...)
      /ppt/slideMasters/           masque (style commun)
      /ppt/theme/                  couleurs et polices du thème
      /ppt/media/                  images
      /ppt/notesSlides/            notes du présentateur
      [Content_Types].xml et les fichiers _rels : déclarent les parties et leurs liens
  - Objets d'une diapositive : p:sp (forme ou texte), p:pic (image), p:graphicFrame
    (tableau / graphique), p:grpSp (groupe), p:cxnSp (connecteur).
  - Unités : l'EMU. 914 400 EMU = 1 pouce ; 12 700 EMU = 1 point ; 9 525 EMU = 1 unité WPF
    (96 DPI). Diapositive 16:9 = 12 192 000 x 6 858 000 EMU = 1280 x 720 unités WPF.
    Diapositive 4:3 = 9 144 000 x 6 858 000 EMU = 960 x 720 unités WPF.
  - Héritage : une forme n'indique pas toujours sa position ni sa police ; elle les hérite
    de sa disposition, puis du masque, puis du thème. C'est la partie la plus difficile de
    la lecture d'un fichier -> fichier PptxThemeResolver.cs (Membre 1).
  - Validation : le SDK fournit OpenXmlValidator pour vérifier qu'un fichier généré respecte
    la norme. On l'utilise dans les tests (PptxRoundTripTests.cs).

2.6 Critères d'acceptation (la démonstration finale doit réussir tout cela)
  C1  Créer 5 diapositives avec texte, formes et image, enregistrer, puis ouvrir le fichier
      dans PowerPoint ou LibreOffice Impress sans erreur.
  C2  Ouvrir un .pptx créé dans PowerPoint (titre, texte, formes, images simples) : les
      objets apparaissent au bon endroit avec le bon texte.
  C3  Modifier, enregistrer, rouvrir dans Weak Point : le résultat est identique.
  C4  Ctrl+Z annule toutes les actions d'édition (et Ctrl+Y les rétablit).
  C5  Le diaporama fonctionne depuis la première diapositive et depuis la courante.
  C6  Un fichier contenant des objets non gérés s'ouvre sans plantage, et ces objets sont
      toujours présents après enregistrement.
  C7  Les tests unitaires passent ; le manuel et le rapport sont livrés.

3. CHOIX TECHNIQUES
==============================================================================

  Langage / plateforme : C# sur .NET 10. .NET 10 est une version LTS (support de 3 ans),
      publiée en novembre 2025. Si un membre n'a que le SDK .NET 8, changer la seule ligne
      <DotNetTfm> dans Directory.Build.props.
  Interface : WPF (Windows uniquement). Pourquoi : dessin vectoriel natif, Canvas,
      transformations (rotation), Adorners (poignées de sélection), RichTextBox. En
      WinForms il faudrait tout dessiner à la main ; MAUI / Avalonia sont multiplateformes
      mais bien plus lourds pour un projet scolaire.
  Lecture / écriture .pptx : paquet NuGet « DocumentFormat.OpenXml » (SDK Open XML officiel
      de Microsoft, version 3.5.1 au moment de la rédaction). Pourquoi : lit et écrit les
      .pptx sans installer Office. Interdit : l'interop COM avec PowerPoint (exigerait
      Office installé, ce qui serait de la triche pour une « réplique »).
  Organisation du code : MVVM (Modèle - Vue - VueModèle) pour séparer les données, l'écran
      et la logique d'écran : chaque membre travaille dans « sa » couche sans casser les
      autres.
  Annuler / Rétablir : pattern « Command » (chaque modification est un objet avec Execute()
      et Undo()). C'est la méthode standard ; elle doit être en place TÔT car toute
      modification en dépend.
  Tests : xUnit. Le projet Core ne dépend pas de WPF précisément pour pouvoir être testé.
  Fichiers récents / réglages : JSON via System.Text.Json (inclus dans .NET).

4. ARCHITECTURE DE L'APPLICATION
==============================================================================

  3 projets dans une solution :

     WeakPoint.UI (WPF)    ───────►  WeakPoint.Core (bibliothèque, SANS WPF)
       Views (XAML)                    Models   : Presentation, Slide, éléments
       ViewModels                      Pptx     : lecture / écriture .pptx
       Editor (canvas, outils)         Commands : annuler / rétablir
       Rendering                       Utils    : conversions, identifiants
       Services (fichiers, export)
                                     WeakPoint.Tests ──► Core

  Règle d'or n°1 : le Core ne référence JAMAIS WPF (pas de System.Windows). Pourquoi : il
      reste testable automatiquement et indépendant de l'écran.
  Règle d'or n°2 : le MODÈLE (Presentation, Slide, éléments) est la seule source de vérité.
      L'écran n'en est que le reflet. Pourquoi : enregistrer, annuler et dessiner
      deviennent simples et cohérents.

  Flux « Ouvrir un fichier » :
     Bouton Ouvrir -> MainViewModel -> DialogService (choix du fichier) -> PptxReader
     -> Presentation -> SlideViewModel -> SlideRenderer -> SlideCanvas (affichage)

  Flux « Déplacer un objet » :
     Souris -> SelectTool -> MoveElementAction -> UndoRedoManager.Execute()
     -> modifie le modèle -> l'écran se rafraîchit ; Ctrl+Z appelle Undo() sur l'action.

5. RÉPARTITION DES TÂCHES ENTRE LES 4 MEMBRES
==============================================================================

Principe : chaque membre possède des fichiers précis (voir section 6) et seul le
propriétaire d'un fichier le modifie. Les difficultés sont réparties ainsi :
  M1 et M2 -> les deux moteurs difficiles (format .pptx / moteur d'édition)
  M3       -> la couche « interface graphique (GUI), mise en forme, vignettes, diaporama »
              (difficulté moyenne)
  M4       -> les services et briques autonomes (moins complexes, bien délimitées)
Nombre de fichiers : M1 = 30, M2 = 23, M3 = 28, M4 = 22. Le nombre de fichiers n'est pas
l'unité de charge : ceux de M1 et M2 sont longs et difficiles (moteur .pptx, moteur
d'édition), ceux de M4 sont courts, autonomes et simples (M1 compte aussi les fichiers de
configuration du dépôt).

RESPONSABLE GUI : le Membre 3 est le SEUL responsable de l'interface graphique (GUI), pour que
l'application garde un aspect cohérent. Il possède tous les fichiers XAML de vues (dossier
Views/, avec Dialogs/ et Popups/), les ressources (Resources/ : Colors.xaml, ControlStyles.xaml,
icônes) et les convertisseurs XAML (Converters/). Les autres membres n'écrivent ni vue XAML ni
style : ils utilisent les couleurs et styles de Colors.xaml / ControlStyles.xaml, y compris pour
les éléments dessinés en code (ex. poignées de SelectionAdorner). Les ViewModels restent à leur
propriétaire : M3 s'y connecte par binding. App.xaml et MainWindow.xaml restent à M1 (fichiers
sensibles, règle R6) : M1 y assemble les vues de M3 sans les restyler.
Pour équilibrer la charge, les actions annulables sur les diapositives (Add / Delete /
Duplicate / Move) et leurs tests passent de M3 à M4.

==============================================================================
7. RÈGLES DE TRAVAIL AVEC GITHUB
==============================================================================

  R1  La branche « main » est réservée à la version finale : personne n'y pousse pendant le
      projet. Seules exceptions : le tout premier envoi du squelette par M1 (section 9,
      étape 2) et, à la fin du projet, l'unique fusion « dev » -> « main » faite par M1
      (Phase 6). Pourquoi : main doit toujours compiler ; c'est la version que l'on présente.
  R2  Chaque membre travaille sur SA branche personnelle, nommée m1, m2, m3 ou m4 (une seule
      par membre, créée à partir de « dev » et gardée pendant tout le projet). Le travail
      terminé et testé est envoyé vers la branche « dev » (voir R4). « dev » rassemble le
      travail de toute l'équipe : elle doit toujours compiler.
      Pourquoi : on isole le travail en cours, on peut le relire avant de l'intégrer, et « dev »
      sert de zone d'intégration sans toucher à « main ».
  R3  Petits commits, messages en français avec un préfixe :
         feat: ajoute la rotation des éléments        fix: corrige le calcul des EMU
         docs: met à jour la documentation            test: ajoute les tests d'EmuConverter
         refactor: simplifie le rendu des formes      chore: ajuste le .gitignore
  R4  Tout envoi vers « dev » passe par une Pull Request (PR) de sa branche personnelle vers
      « dev », relue par un AUTRE membre :
         M1 <-> M2 se relisent mutuellement ; M3 est relu par M1 ; M4 est relu par M2.
      Le relecteur vérifie : ça compile, les tests passent, le code est compréhensible.
  R5  Chacun ne modifie QUE ses fichiers. Pour un autre fichier : ouvrir une « Issue »
      GitHub ou demander au propriétaire. Pourquoi : c'est la meilleure façon d'éviter les
      conflits de fusion.
  R6  Fichiers sensibles, modifiés uniquement par M1 : *.csproj, *.sln,
      Directory.Build.props, App.xaml, MainWindow.xaml, MainViewModel.cs. Pourquoi : tout le
      monde en dépend et les conflits y sont difficiles à résoudre (surtout le XAML).
  R7  Avant chaque push : « dotnet build » puis « dotnet test ». Jamais de code qui ne
      compile pas.
  R8  Suivi : une Issue GitHub par fonctionnalité (F01, F02...) et un tableau Kanban
      (onglet Projects) À faire / En cours / En relecture / Terminé.
  R9  Fichiers .pptx de test : petits (< 1 Mo) et uniquement dans tests/.../TestFiles/.
  R10 Chaque matin : « git pull » sur dev puis on fusionne dev dans sa branche personnelle
      (git merge dev). Pourquoi : on découvre les conflits tôt, quand ils sont petits.
  R11 Interface graphique : seul M3 (responsable GUI) crée ou modifie les fichiers XAML de
      vues, les styles (Resources/) et les convertisseurs (Converters/). Pourquoi : un seul
      responsable garantit un aspect cohérent.

==============================================================================
8. PLANNING PAR PHASES  (par priorité, SANS date limite)
==============================================================================

Il n'y a pas de date limite : on avance le plus vite possible. L'ordre des phases suit les
priorités de la section 2.3 : d'abord tout ce qui est nécessaire pour que l'application soit
utilisable comme un PowerPoint de base (toutes les fonctions P1, phases 0 à 3), puis seulement
les fonctions P2 et P3 (phase 4). Un membre n'attaque une fonction P2 ou P3 qu'une fois ses
propres tâches P1 terminées.

PHASE 0 — FONDATIONS
   M1 : dépôt GitHub (branches main et dev), structure, Models + interfaces (PR « contrat »
        vers dev fusionnée en 3 jours max), MainWindow vide.
   M2 : IUndoableAction, squelette d'UndoRedoManager, maquette du SlideCanvas qui affiche
        un rectangle.
   M3 : apprendre MVVM / binding, Colors.xaml et ControlStyles.xaml (style commun),
        maquettes XAML du ruban et des vignettes (données factices).
   M4 : EmuConverter + tests, README.
   Jalon : l'application démarre (fenêtre vide), build et tests verts sur dev.

PHASE 1 — PREMIER CYCLE DE BOUT EN BOUT
   M1 : PptxReader / PptxWriter pour texte et formes simples ; Nouveau / Ouvrir /
        Enregistrer branchés.
   M2 : SlideRenderer (texte, formes, images) + sélection et déplacement.
   M3 : vignettes (clic = changer de diapo), ruban branché (dont les boutons ajouter /
        supprimer une diapo), StatusBarView.
   M4 : DialogService, RecentFilesService, StatusBarViewModel, AddSlideAction /
        DeleteSlideAction, fichiers .pptx de test.
   Jalon : on ouvre un .pptx simple, on l'affiche, on déplace un objet, on enregistre
           (F02, F03, F05, début de F11).

PHASE 2 — ÉDITION COMPLÈTE
   M1 : images (avec M3), héritage disposition / masque (PptxThemeResolver),
        UnsupportedElement (F28).
   M2 : redimensionner, pivoter, texte en place, annuler / rétablir complet,
        copier-coller, ordre Z.
   M3 : FormatPanel, dispositions, fond, glisser-déposer des vignettes, mappers texte / forme,
        vues NewPresentationDialog, galerie de formes, sélecteur de couleurs, NotesPanel.
   M4 : DuplicateSlideAction, MoveSlideAction, NotesViewModel.
   Jalon : critères C1, C3, C4.

PHASE 3 — DIAPORAMA ET FIDÉLITÉ (fin des fonctions P1 : PowerPoint de base)
   M3 : SlideshowWindow (F18).
   M1 : validation avec OpenXmlValidator, tests aller-retour sur de vrais fichiers.
   M2 : performances.
   M4 : compléter les tests unitaires et la collection de .pptx de test, commencer le
        manuel utilisateur.
   Jalon : critères C2, C5, C6. Toutes les fonctions P1 sont livrées : l'application est
           utilisable comme un PowerPoint de base.

PHASE 4 — FONCTIONS P2, PUIS P3 (après la version de base)
   M3 : transitions (F24, PptxTransitionHandler), avec l'aide de M1.
   M2 : guides d'alignement (F22), groupes (F23).
   M4 : ExportService (PNG, F25), PptxNotesHandler (F21), avec l'aide de M1.
   Les autres fonctions P2 de la section 2.3 (F26, F27, F29) sont ensuite prises par le
   membre disponible, dans sa couche ; puis les fonctions P3, une par une.
   Chaque fonction terminée est envoyée vers « dev » dès qu'elle est stable.

PHASE 5 — FINITIONS
   Quand l'équipe décide d'arrêter d'ajouter des fonctions : gel des fonctionnalités
   (« feature freeze »), plus de nouvelle fonction, seulement des corrections. Tests, manuel
   utilisateur, rapport, préparation de la démonstration (le scénario C1 à C7, répété
   plusieurs fois).

9. MISE EN ROUTE PAS À PAS (AVEC LE « POURQUOI »)
==============================================================================

ÉTAPE 1 — Tout le monde : installer les outils.
   Installer le SDK .NET 10, puis dans cmder : dotnet --version
   Installer dans VS Code l'extension « C# Dev Kit » et vérifier que « git --version » marche.
   Pourquoi : le SDK compile le code ; l'extension donne l'auto-complétion et le débogage ;
   vérifier maintenant évite de découvrir un problème d'installation en pleine Phase 1.
   (Si votre SDK est .NET 8 : changer <DotNetTfm> en net8.0 dans Directory.Build.props.)

ÉTAPE 2 — Membre 1 : créer le dépôt et publier le squelette.
   Sur github.com : créer un dépôt vide « WeakPoint » (sans README), inviter les 3 autres
   membres en « Collaborators ». Puis, dans cmder, dans le dossier du squelette dézippé :
      git init -b main
      git add .
      git commit -m "chore: structure initiale du projet"
      git remote add origin https://github.com/<pseudo>/WeakPoint.git
      git push -u origin main
      git switch -c dev
      git push -u origin dev
      git switch -c m1                 (branche personnelle de M1)
   Pourquoi : « init » crée l'historique local ; « add » + « commit » enregistrent une
   première version ; « remote add » relie le dossier à GitHub ; « push » envoie le tout.
   « switch -c dev » crée la branche d'intégration « dev », publiée par le second push ;
   « switch -c m1 » crée la branche de M1. Ce premier push sur main est le seul avant la fin
   du projet (voir R1).

ÉTAPE 3 — Membres 2, 3, 4 : récupérer le projet.
      git clone https://github.com/<pseudo>/WeakPoint.git
      cd WeakPoint
      git switch dev
      git switch -c mX                 (SA branche personnelle : m2, m3 ou m4)
   Pourquoi : « clone » télécharge le projet ET son historique, et le lie à GitHub. On crée
   ensuite sa branche personnelle à partir de « dev ».

ÉTAPE 4 — Tout le monde : vérifier que le squelette compile.
      dotnet restore      (télécharge les paquets NuGet : OpenXml, xUnit)
      dotnet build        (compile les 3 projets)
      dotnet run --project src/WeakPoint.UI
   Une fenêtre « Weak Point — squelette du projet » doit s'ouvrir.
   Pourquoi : si ça marche chez tout le monde, on part d'une base commune saine. Le
   squelette n'a pas pu être compilé là où il a été généré (pas d'environnement Windows) :
   si une erreur apparaît, prévenir M1 immédiatement, c'est le moment de la corriger.

ÉTAPE 5 — Membre 1 : sécuriser GitHub.
   Remplacer les PSEUDO-MEMBRE-x dans .github/CODEOWNERS par les vrais pseudos. Dans
   Settings > Branches : protéger « main » ET « dev » (Pull Request obligatoire, 1 approbation).
   Pourquoi : on empêche mécaniquement les pushs directs et on automatise la relecture.

ÉTAPE 6 — Chacun : cycle de travail quotidien.
      git switch dev ; git pull                       (récupérer le travail des autres)
      git switch mX ; git merge dev                   (mettre SA branche à jour ; mX = m1..m4)
      ... coder dans SES fichiers ...
      dotnet build ; dotnet test                      (vérifier avant de partager)
      git add . ; git commit -m "feat: ..." ; git push -u origin mX
      puis ouvrir la Pull Request sur GitHub (de mX vers dev), demander la relecture, puis
      fusionner avec « Create a merge commit » (pas « Squash » : la branche personnelle est
      gardée pendant tout le projet).
   Pourquoi : chaque étape est un filet de sécurité (branche personnelle -> tests ->
   relecture) qui protège « dev », la branche d'intégration. « main », la version que l'on
   présentera, n'est touchée qu'une seule fois, à la fin (Phase 6).

ÉTAPE 7 — Réunion de lancement (30 min) : confirmer les hypothèses H1 à H5, ouvrir les
   Issues F01 à F20 et assigner chacune au bon membre selon la section 5.
